# Logs whose measured code has moved since they were taken.
# Written by scripts/check_figure_staleness.py --update-baseline.
# A log leaves this list by being RE-TAKEN, not by being edited.
# Adding a line here is a decision to publish a figure that is known
# not to describe the current code, and belongs in review.
#
# This baseline is the repository's state when the gate was introduced. It is not a
# clean slate -- it is the backlog the gate exists to stop growing.
#
# Each line records WHICH files moved under that log. A log fails when that set
# GROWS, so being listed here does not excuse the next change to the code beneath
# it. A log leaves the list by being re-taken.
#
# FOUR CAUSES, and they are not the same thing.
#
# 1. MOST of these predate commits that genuinely changed the kernels they
# measure. Those figures may well be wrong, and only a re-take can say.
#
# 2. Some went stale on a bit-identical narrowing fix to QuantMat<1,W>::set, a
# header every benchmark includes, landed to make verify_cortex_m.sh pass.
#
# 3. The optical-flow logs went stale on a NEON lane index becoming a template
# parameter rather than an int -- a fix for a Debug build that would not
# compile at all. Checked rather than assumed: the same translation unit built
# at -O3 on the reference device before and after gives IDENTICAL OPCODE
# HISTOGRAMS, 18711 instructions either way, differing only in which register
# the allocator chose in six spill pairs. The figures are still true of that
# code, so they are accepted here rather than re-taken.
#
# 4. Five logs -- corner_subpix-aarch64, dense-aarch64, dense-x86_64,
# feature-aarch64 and features-x86_64 -- went stale on ops/pack.hpp and
# ops/fast.hpp being made instantiable from a .cu without warnings, and on the
# bit-plane FAST gate moving out of its row loop. Checked the same way, and more
# tightly: every function of corner_subpix_benchmark, dense_benchmark and
# feature_benchmark was disassembled before and after, on BOTH architectures,
# with addresses normalised out. Zero functions differ in any of the six
# binaries. The only function that differs anywhere is detectFast<uint32_t>, and
# the two logs that measure IT were re-taken rather than listed here.
#
# 5. The two CUDA sweeps went stale on a block-size sweep of three constants, and every figure QUOTED from them is still true. Checked per row rather than assumed: descriptor's kRefBlock and orientation's kRefBlock size only the FALLBACK arms, and the published rows take neither -- a 256-bit descriptor is 8 words against the ballot arm's 32-word cap, and ORB's radius 15 satisfies the warp arm's radius <= 15 -- while covariance's kRegionBlock has no published row at all and is a null below gridFor's 4096-block cap. The benchmarks' own off-switch controls DO reach the changed arms, which is why the gate fires and is right to; no published figure does. They leave this list at the next re-take on an unloaded host.
#
# 6. The pre-release documentation pass (2026-09-28) touched code lines in headers
# every benchmark includes: an #include added in core/view.hpp, core/parallel.hpp,
# threads/pool.hpp and ops/edge.hpp; BINCV_ASSERTs added in ops/pack.hpp and
# ops/denseDisparity.hpp (compiled out under NDEBUG); a dead store pair removed
# from impl/binMat_impl.hpp; two unused functions removed from ops/pyramid.hpp;
# __builtin_ctzll moved behind impl::ctzWord in ops/subpix.hpp; and a runtime
# off-switch around stagedCovariance's NEON arm in ops/opticalFlow.hpp. Checked
# rather than assumed on x86-64: every benchmark behind a newly stale log was
# built at 7cf195d and at the edited tree, Release with the same flags, and
# disassembled with addresses normalised out -- all nineteen are
# INSTRUCTION-IDENTICAL, so the x86-64 figures are still true of this code. On
# aarch64 the same lines compile the same way except the one NEON region that
# changed, stagedCovariance: the device rows that run the tracker gained one
# predictable branch per point per level, and rather than argue it they were
# RE-TAKEN on the device at 4c4b3bf (lk_headtohead, feature-tracking,
# lk_memorybound; ten launches each, clock sampled at 1.80 GHz throughout) --
# every cell landed inside its previous interval, and those three logs are
# fresh. The spot-check log of the pipeline keeps its earlier stamp. The CUDA
# sweeps went stale on launcher-side refusals (argument checks before a launch;
# no kernel changed) and on benchmark-source edits: the kernel-resident timings
# are unaffected and the wall-clock rows gain a few host compares; a re-take on
# an unloaded host is owed for those too.
#
# 7. Every log now carries a `# sources:` line (each measured file with a hash of
# its comment-stripped content), backfilled from the commit it stamps while that
# commit still existed locally, so the gate reads the same on every clone. That
# made bitwidth_crossover-x86_64-launches.log mappable for the first time -- it
# had named a launcher outside the repository -- and it is stale under the same
# header edits as the rest of cause 6 plus the sweep script's own comment. Its
# figures are the x86-64 column of limits.md's crossover table, which that page
# says predates the benchmark's build change and stands until re-taken; on that
# host the two pyramid benchmarks agreed before the change (32.20 against
# 32.40 us). It leaves this list at the next x86-64 re-take.
#
